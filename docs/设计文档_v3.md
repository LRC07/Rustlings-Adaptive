# RustLings-Adaptive 设计文档（v3）

> 相对 v2 的变更（本轮迭代吸收的想法已逐条落位）：
> 1. **知识锚点改双轨**：错误码（E0xxx）保留为"粗轨"——可靠但粒度粗；
>    新增**细分概念图谱**作"细轨"（`taxonomy/concepts.toml`，机器可运营）。
>    信号源从单一编译诊断扩展为**五类**（编译诊断 / 测试失败 / 修复模式 /
>    clippy / 复盘表现）。背景：用户本地有 rust-analyzer，编译错误常在
>    跑到 CLI 之前就被修掉，单靠 E0xxx 会漏信号；"测试全绿"也不等于改得好。
> 2. **新增解答评审门**：测试通过后，LLM 对"模板 → 用户解"做逻辑评审，
>    从失败测试与非最优改法中提取信息（多余 clone、手动循环代替迭代器、
>    硬编码期望值等），据此决定复盘形态。
> 3. **复盘改交互式分支**：原理解释支持**选择题或自由输入**；评审门发现
>    更优解时给方向性提示，用户可再试或查看解答；对比总结后记录掌握度，
>    并由 Agent **决定是否再出一道相关题**（变式 / 加约束 / 升难度）。
> 4. **题目模型新增抽象约束**（constraints）：如 no-clone、iterators-only、
>    max-lines，机器可校验的部分由静态检查硬判，作为"设计习惯训练"载体。
> 5. **定位强化"小片段主义"**：项目的亮点是把复杂场景规约到一个个小的
>    片段，质量易把握、便于针对性指导与统计数据；P2 新增"真实代码片段
>    → rustling"的规约管线。
> 6. 题目模板格式定为 TOML；槽位规格给出最小 schema（未决项收窄）。

## 1. 产品定位

一个**对话式 Rust 诊断教练** Agent。用户在 CLI 中用自然语言提问/贴代码，
Agent 解释、必要时**在对话中即时插入一道针对性填空题**作为验证；题目不强
求独立构成完整题库，只要求"与当前上下文相关、能暴露薄弱点、机器可解"。

- **给谁用**：正在学 Rust 的开发者（含本课程同学），卡在所有权/借用、
  生命周期、泛型、trait 等编译期概念上的人。
- **解决什么**：rustlings 固定无个性化；通用 LLM 能解释但不会本地验证、
  不记错误、无法在对话中即时出可练的题。本 Agent 把"解释 → 验证 → 诊断
  → 复盘 → 归档 → 定向巩固"做进同一对话。
- **教学立场**：不只补语法漏洞，更借小片段培养设计习惯——直接改大段真实
  代码难以下手，但确定的 rustling 场景小而可控，适合从一个个小模块中学
  习更好的设计思路。

### 1.1 设计原则：小片段主义

1. **小片段优先**：题目 10–40 行、聚焦 1–2 个概念、机器可判。复杂场景
   一律先规约成小片段再教学——这是全项目的核心方法论，也是质量可控、
   统计可行的前提。
2. **真实执行为据**：解释、出题、评审、复盘都必须有 rustc / 测试 / 实测
   数据背书，不靠模型主观判断。
3. **一切信号落数据**：每次交互产出结构化记录（五类信号），单次稀疏也能
   逐步积累成画像。

## 2. 目标用户与痛点

| 痛点 | 现状 | 通用 Agent 为何解决不好 |
|---|---|---|
| 同类错反复犯 | rustlings 不记错误 | 无持久状态 |
| 解释完不知是否真懂 | 用户"我懂了"不可信 | 无可执行验证手段 |
| LLM 给的题常不可编译 | 直接生成代码带错 | 不本地跑 rustc |
| 借用报错看不懂 | 模型从文本猜常错 | 无真实编译器还原因果 |
| 本地有 rust-analyzer，编译错误在 CLI 前已被修掉 | 编译错误码采集不到 | 信号源只有编译诊断一条路 |
| 错误码粒度太粗，同一码下短板各异 | E0277 下可能是十种不同错 | 无细分概念体系，锚点不精确 |
| 测试全绿 ≠ 改得好 | 多余 clone、手动循环等非最优改法无人指出 | 不做本地逻辑评审 |
| 改大段真实代码无从下手 | 缺小步、可对照的练习载体 | 无"小片段 + 约束 + 多解对比"机制 |

根本原因：通用 Agent **既缺持久状态，也无法可靠本地执行与校验代码**。

## 3. 场景定制（通用 Agent 做不到的事）

1. **rustc 即工具 + 三重校验**：任何要给用户的题（模板或生成）必过本地
   `rustc --test` 三重校验（能编译 / 参考解全绿 / todo 模板必失败）。
2. **双轨知识锚定 + 多源信号**：细轨是细分概念图谱（一个概念 = 一个能用
   10–40 行片段孤立考察的点，如 `borrow.split-fields`、
   `traits.assoc-type-vs-generic-param`），粗轨是 rustc 错误码，二者互为
   校验（模板标注码与真实不符 → 反哺修正）。信号源五类：编译诊断、测试
   失败、修复模式（用户解与模板的 diff 特征）、clippy lint、复盘表现。
   全部归一为带权重的 Signal 入画像。
3. **解答评审门**：测试通过 ≠ 结束。静态检查（todo!/unimplemented! 残留、
   约束、clippy）+ LLM 逻辑评审（题面 + 模板 + 用户解 + 测试结果 →
   clean / suggestions / suspicious），从失败测试与非最优改法中提取信息；
   suspicious（如硬编码期望值、擦边通过）加探测测试再验。
4. **交互式复盘**：通过后，Agent 复现原失败代码与真实诊断，请学习者解释
   "为什么之前不过、现在能过"（**选择题或自由输入皆可**），据真实错误码
   与根因关键词校核；发现更优解时**给提示让用户再试或查看解答**；最后
   给出实测对比总结（行数 / clippy / 编译时长 / 运行时 / 约束满足），
   记录知识掌握情况，**决定是否再出一道相关题**。
5. **可校验的抽象约束**：题目可附抽象修改约束（no-clone、iterators-only、
   max-lines…），静态可判的机器硬判，其余 LLM 判定 + 实测佐证。约束是
   "逼出更优解"的脚手架，直接服务设计习惯培养。
6. **借用检查器假设实验室（招牌，P1）**：假设性改代码 → rustc → 诊断
   增量（旧 E0xxx → 新 E0xxx），让借用规则因果可观察。
7. **错题本 + 检索闭环**：每条错误归档（错误码、概念、最小复现、修复、
   用户解释、评判）；下次同码/同概念出错检索相似旧错。持久状态 + 检索。

## 4. 核心交互流程

CLI 主体是**对话 REPL**（满足 R2），辅以菜单跳转。

### 4.1 对话诊断（主流程）
```
用户：贴一段报错代码 / 问概念（"为什么这里要 &mut self"）
  → Agent：解释 + 双轨锚定（错误码 → 概念图谱节点）
  → [若需巩固] Agent 调用工具生成/选一道填空题（三重校验后展示）
用户：在 $EDITOR 补全 → [r] 运行
  → Agent：rustc --test 实时结果
      失败：错误码级反馈 + 从失败断言提取"下一步提示"（不直接给答案）
      通过：进入解答评审门（4.2）
```
长任务（LLM/编译 >3s）显示进度，Ctrl-C 打断（R4）。

> **界面定位（定稿）**：启动即进入**对话界面**（REPL 是默认首屏，M4 落地）；
> 类 rustlings 的做题界面是**子模式**，由对话中出题触发或按需进入。
> `exercises/` 现有 8 道种子题的定位是**开发期 fixture 与演示素材**，
> 不构成最终产品的默认界面内容（M8 收尾时决定 fixture 化或移除）。
>
> **编辑器接入（定稿）**：做题编辑不再绑死 vi。解析优先级：
> `$EDITOR` / `$VISUAL` → config.toml `editor` 字段 → 自动探测 VS Code
> （`code --wait <file>`，`--wait` 保证 CLI 阻塞等待编辑完成）→ vi 兜底；
> 配置页 `[c]` 可交互修改。
> 取舍：在 VS Code（rust-analyzer 子 crate）里编辑时，行内诊断直接可见、
> 用户常在保存前就修完编译错误，CLI 侧编译反馈不再是主信息源——这正是
> §3.2 多源信号设计的根据：**细轨概念标签与测试结果比错误码更可靠**，
> 错误码降级为机会性信号（拿到就用，拿不到不依赖）。

### 4.2 解答评审门
```
[测试全绿]
  → 静态检查：todo!/unimplemented! 残留、constraints 静态项、clippy、行数
  → LLM 逻辑评审（题面 + 模板 + 用户解 + 测试结果 → JSON）：
      verdict = clean | suggestions | suspicious
      findings = [{kind, severity, message, better_way}]
  → clean        → 进复盘（解释环节可轻量）
  → suggestions  → 复盘 Step 2 触发"更优解挑战"
  → suspicious   → 自动加一道探测测试再验；仍可疑 → 不计掌握，标记归档
```
非最优改法示例：能用 `&str` 处处 `String`、能拆分借用却 clone 逃逸、
手动 for 循环可写成迭代器链、match 可写成 `matches!`。

### 4.3 交互式复盘（分支）
```
Step 1 原理解释（之前为什么不过 / 现在为什么能过）
  Agent 据真实诊断 + 概念生成 3–4 个选项（1 正确根因 + 2–3 常见误解）
  用户：[数字] 选择 或 直接输入文字
  校核：选择题直判；自由输入由 LLM 对照真实错误码 + 根因关键词判 hit/miss
  （一次通过无失败快照时，改为问"这题考什么 / 模板为什么会失败"）
Step 2 更优解挑战（评审门 verdict ≠ clean 或与参考解风格差异大时触发）
  Agent 只给方向性提示（"这一步可以用迭代器一次完成"），不给答案
  用户：[r] 带提示再改一次   /   [s] 查看参考解与对比
Step 3 对比总结
  用户解 vs 参考解（±惯用解）：行数 / clippy 警告 / 编译时长 /
  运行时（可选）/ 约束满足  → 表格 + Agent 一句话点评取舍
Step 4 归档与决策
  SM-2 更新概念节点（尝试次数 / 是否用提示 / 解释命中 / 约束满足）
  decide_follow_up：
      一次通过 + 解释命中 + clean          → NextConcept（下一概念）
      通过但解释 miss 或用了提示           → Variant（同概念换槽位变式）
      通过但约束未满足 / suggestions       → Variant + 附加约束
      ≥3 次失败                            → 降难度 Variant + 引导看错题本旧错
```

### 4.4 自然触发出题的几种形态
- 用户报错 → 解释后问"要不要做道类似的题巩固"
- 用户连续两次同概念错误 → 主动插入诊断题
- 用户说"我懂了" → 用一道题验证（不信主观判断）
- 测试全绿但评审门 suspicious → 探测测试验证真懂

### 4.5 借用实验室 / 统计
- borrowlab：贴代码 + 假设性改动 → 诊断 diff + 解读
- stats：概念图谱（SM-2）、错题本、token/花费

## 6. 数据源

| 数据 | 来源 | 用途 |
|---|---|---|
| 编译诊断（结构化） | `rustc --error-format=json` | 验证、粗轨锚点、诊断增量 |
| 测试结果（含失败断言 expected/actual） | `rustc --test` 运行 | 评审门、细轨信号 |
| clippy 诊断 | `cargo clippy --message-format=json` | 评审门、多解对比（P0 即用） |
| 用户修复 diff | 模板 ↔ 用户解 | 修复模式信号（中权重） |
| LLM | OpenAI 兼容 API（含 function/tool calling） | 解释、填槽、评审、复盘、解读 |
| 题目模板 | 手写 `templates/*.toml` | 生成基座 |
| 概念图谱 | 手写 `taxonomy/concepts.toml`（repo 内版本化） | 细轨锚点、画像、定向 |
| 错误码释义 | rustc error index（可选抓取） | 解释辅助 |
| 用量与价格 | API usage + 配置价格表 | R6 |

### 7.2 关键数据结构

```rust
// ===== 概念图谱（细轨锚点，repo 内版本化）=====
struct ConceptNode {
    id: String,                    // "borrow.split-fields"
    name: String,
    parents: Vec<String>,          // 图谱边：上位概念
    error_codes: Vec<String>,      // 常触发码（与粗轨互为校验，多对多）
    fix_patterns: Vec<String>,     // 常见修复模式标识
    templates: Vec<String>,        // 覆盖该概念的模板 id
}
// 用户侧掌握度（SM-2），存 ~/.rustlings_adaptive/concept_state.json
struct ConceptState {
    concept: String,
    mastery: f32, ease: f32, interval_days: u32, last_review: Option<DateTime>,
}

// ===== 五类信号（统一入口，带权重）=====
enum Signal {
    CompileError { code: String, span: Span },               // 强
    TestFailure { test: String, expected: String, actual: String }, // 中强
    FixPattern { kind: FixKind },                            // 中（LLM 从 diff 判）
    ClippyLint { lint: String },                             // 弱-中
    ExplanationMiss { concept: String },                     // 弱
    ConstraintMiss { constraint: String },                   // 中
}
// 权重初值：1.0 / 0.8 / 0.6 / 0.4 / 0.5 / 0.6（可调）

// ===== 题目模板（TOML）=====
struct Template {
    id: String,
    concepts: Vec<String>,         // 细轨概念 id（≤2 个）
    error_codes: Vec<String>,      // 粗轨：此题做错时常触发的码
    difficulty: Difficulty,
    code: String,                  // 含 {{slot}} 占位与 // TODO
    slots: Vec<SlotSpec>,          // kind: ident | type | literal
    tests: Vec<TestCase>,
    reference_solution: String,
    constraints: Vec<Constraint>,  // 抽象修改约束
    review_hints: Option<ReviewHints>, // 根因关键词 + 误解选项种子
}

// ===== 抽象约束 =====
enum Constraint {
    NoClone,                       // 禁 .clone()/.to_owned()      静态
    NoUnwrap,                      // 禁 unwrap/expect             静态
    IteratorOnly,                  // 禁 for/while 循环            静态
    MaxLines(u32),                 //                              静态
    SinglePass,                    // 禁嵌套循环                   半静态+LLM
    CustomStatic { ban: Vec<String> },   // 禁用 token 序列         静态
    CustomJudged { rubric: String },     // LLM 按 rubric 判        判定
}
// 质量门要求：参考解必须满足模板自己声明的全部静态约束（自洽校验）

// ===== 解答评审门 =====
enum ReviewVerdict { Clean, Suggestions, Suspicious }
struct SolutionReview {
    verdict: ReviewVerdict,
    findings: Vec<Finding>,        // {kind, severity, message, better_way}
    probe_test_added: bool,        // suspicious 时加探测测试再验
}

// ===== 交互式复盘 =====
enum Explanation {
    Choice { options: Vec<String>, answer: usize, pick: Option<usize> },
    Free { text: String },
}
struct BetterSolutionChallenge {
    hint: String,                  // 方向性提示，不含答案
    retried: bool,
    final_code: Option<String>,
}
struct ReviewRound {
    failing_snapshot: Option<String>,   // 最后一次失败代码（一次过则 None）
    diagnostics: Vec<Diagnostic>,
    explanation: Explanation,
    explanation_hit: ExplanationCheck,  // 是否命中真实错误码/根因
    challenge: Option<BetterSolutionChallenge>,
    comparison: ComparisonTable,        // 行数/clippy/编译时/运行时/约束满足
    follow_up: FollowUpDecision,        // None | Variant | Harder | NextConcept
}

// ===== 三重校验 / 诊断（同 v2）=====
struct VerifyReport { compiles, ref_solution_passes, template_fails, diagnostics }
struct Diagnostic { code: Option<String>, message: String, severity, spans }

// ===== 错题本 / 画像 / 配置 / 用量（大体同 v2）=====
struct NotebookEntry { id, ts, error_code, concepts, minimal_repro, fix,
                        user_explanation, review: Option<ReviewRound>,
                        related_template }
struct ErrorProfile { by_code: HashMap<String, u32>,
                      by_concept: HashMap<String, ConceptState> }
struct ModelConfig { endpoint, api_key, model, context_len, think_mode,
                     prices, budget, editor: Option<String> }
struct UsageRecord { ts, model, input_tokens, output_tokens, cost, phase }
```

### 7.4 题目质量门（多层布尔，非分数）
1. 硬校验：三重通过（必过）
2. 规则过滤：概念 ≤2、行数 10–40、todo! 数 ≤2、测试直连概念
3. 约束自洽：参考解满足模板声明的全部静态约束（防"题自己都做不到"）
4. 用户反馈：尝试次数/放弃/完成时间/标记"太简单/太难/没意义"
   → 阈值规则降推荐优先级或降档
