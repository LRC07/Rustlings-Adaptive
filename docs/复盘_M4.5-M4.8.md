## 二、做对的决策

1. **规格先于生成**（七条约束 + 规格卡先行）：M4.5d 产稿时 C1 门抓到
   4 处题面/参考解错误（缺 Ok 包裹、move 出 &Tag、deref 强转误解、
   测试数据错误）——真实执行为据的价值持续验证。
2. **单一质量门收口**（gate_draft）：三级出题共用一份门代码；M4.7 的
   max_tokens/预算都加在环上而不是门上，门从未被绕过。
3. **首错误码检查从第一天就抓真问题**：M4.5b 落地即修正 3 个模板的
   error_codes 声明不一致（未完成态的真实首错与声称不符）。
4. **fixture 全轮转质量门**：把 M3"期望值必须由槽位计算"的教训从纪律
   升级为回归测试（每个轮转值过完整 gate，36 模板 × 4 轮）。
5. **失败降级设计化**（M4.7③）：出题工具失败 → 结构化 fallback 指令，
   杜绝了"模型即兴编题绕过质量门"的试用反馈问题。

## 四、★ 超时问题专题（最重要的待解决项）

### 4.1 实测证据链（按时间）

1. paratera 端点（GLM-5.3-Flash）：**短请求（~500 tok 输出）137s 完成
   → ~4 tok/s**，且延迟波动极大（同一请求 140s–500s+）。
2. L3 自由生成的 draft 输出失控：**5.6k / 7.2k / 16.2k tok**（合理体积
   2–3k）——纯 prompt 指令"压缩到 2800 tok"不可靠。
3. 换更快的档案（DeepSeek-V4-Flash / Kimi-K3，同为 paratera 域名）后
   **仍卡在 ~120s**——强烈疑似**网关对非流式请求的硬超时**
   （nginx proxy_read_timeout 120s 是业界默认），不是生成不完。
4. 用户最新实测（M4.7 之后）：**简单 Rc<RefCell<T>> 题约 200s 出题
   成功**——三件套后"勉强能用"，但离顺滑还远。
5. 修复环在慢端点的历史表现：4 轮全超时；逐轮拒绝原因反馈正常
   （max-lines 超限 → 模型改小 → 首错误码不符 → 修正）。

### 4.2 根因分解（乘法模型）

```
总时长 ≈ 轮数 × (排队延迟 + 输出体积 ÷ 吞吐)
```
- 端点侧：吞吐低 + 排队长 + 疑似非流式网关 120s 掐断（换端点无效的
  现象与此吻合）。
- 协议侧：整题 JSON 一次输出（body+tests+reference+转义膨胀 ≈ 2.5–5k
  tok 合理体积）→ 任何慢端点都要 100s+ 单请求。
- 工程侧已缓解：max_tokens 硬限（教育收敛）、420s 预算止损、失败
  fallback、多档案快速切换、逐轮拒绝原因可见。

### 4.3 候选方案（推荐顺序）

1. **分步生成（主推，保险预案已写入设计文档 §8 M4.8）**：把整题 JSON
   拆成 3 个小请求——
   - 步 1 设计卡：场景/根因/错误码/约束选择（~300 tok）
   - 步 2 题面 body（~600 tok）
   - 步 3 tests + reference（~800 tok）
   每步输出 <1k tok，**在最慢端点也能 <120s 完成**；顺带绕开网关
   超时（每步都短）、提升首轮成功率（每步任务简单）、体积天然受控。
   程序在步间组装 + 现有 gate_draft 收口不变。工作量 ~1 天。
2. **流式（stream）请求**：不改变总时长但保持连接有数据流动，绕开
   非流式网关超时。llm client 改 SSE 解析，成本中等。若分步后仍见
   120s 整点失败再做。
3. 治标补充：慢端点下调修复环预算（420s → 240s）+ 出题前在对话里
   提示"该端点较慢，预计 2–5 分钟"。
4. 模板库持续扩容（第 1 级命中率越高，越少走 L3）——批次二剩 7 题
   （闭包三态/Rc-RefCell/Deref/HashMap/悬垂已并入 12b/Result 剥层/
   模块可见性）。

### 4.4 验证方法（新 session 直接可用）

用 `/g <主题>` 直连路径（不走 agent 环）计时；观察逐轮 note；对比
`/model` 切换不同档案；看 `exercises/generated/index.json` 的 attempts。
若出现"120s 整点失败"即网关超时实锤 → 优先做分步生成或流式。

### 4.5 验证结果（9.4 晚真实端点冒烟，M4.10/M4.11 会话执行）

> 总花费 $0.043（147→154 次调用）。L1/L3 各跑一次 + M4.10 去重验证。

1. **M4.7 三件套实测**：
   - 修复环 live 工作：L3 第 1 轮被质量门拒（实际首错 E0594 ≠ 声明的
     E0525——门抓到真实不一致）→ 拒因反馈 → 第 2 轮通过 ✓
   - fallback 收口未实测（需失败场景，单测已覆盖）
2. **M4.8 hints 实测**：L1 模板题 3 条 ✓；L3 自由生成**原为 0**——根因
   = draft prompt 输出格式没要求 hints 字段（M4.11 修复后 3 条 ✓）
3. **★ 120s 网关超时：今天未复现**（吞吐 ~150 tok/s vs 9.4 的 ~4 tok/s），
   L3 端到端 2m40s/$0.0125 与 6m10s/$0.0303——分步生成的紧迫性下降，
   是否还做**等更慢端点实测再定**
4. **★ 新发现：该端点忽略 max_tokens**——请求确定携带 3000（代码路径
   唯一 + 单测），响应仍 19.5k/21.9k/27.5k completion tok，而题面本身
   很紧凑（门全过）→ 大概率是端点侧隐藏推理 token 计入 completion。
   这同时解释了 §4.1"输出体积失控 5.6k–16.2k"的老谜团：可见内容可能
   从来不大，失控的是推理 token。**推论**：prompt 侧"压缩体积"指令从来
   不可能有效（压的是可见部分）；真正的杠杆是换无推理/少推理的模型或
   关闭思考模式（config think_mode 字段仍是预留）
5. **顺带抓到的真 bug（M4.11 修复）**：`/g` 直连路径的 LLM caller 是裸
   闭包，`call_bounded` 走默认实现**直接忽略 cap**——即 M4.7 的硬限在
   `/g` 路径从未真正发出去过（agent 工具路径的 CallerBridge 不受影响）

## 六、试用反馈（9.4 晚，实测会话诊断）

### 6.1 粘贴多行被逐行发送（高频痛点）

- 现象：粘贴约 20 行函数，被按行拆成 **9 条独立消息、9 个 LLM 回合**；
  教练回复 6 次「还差…/你没贴上来」直到片段凑齐（会话消息 [1]–[19]）。
- 现有缓解：``` 围栏粘贴模式（两行 ``` 之间合为一条）——但自然粘贴
  不带围栏，用户不会主动用。
- 修法候选（推荐组合）：
  1. **bracketed paste**：现代终端粘贴自带 `ESC[200~ … ESC[201~` 包裹，
     `cli/input.rs` 的 raw-mode 编辑器可识别并聚合为一条输入（终端
     原生语义，治本）；
  2. **时间启发式兜底**：无包裹时按「行间到达零停顿」聚合（粘贴流
     行间隔 <10ms，人手打字不可能）；
  3. 教练侧无法根治——回合是 CLI 输入层发起的，聚合必须做在输入层。
- **延伸（UI 顺手度 backlog）**：readline 方向键历史（M4.2 曾评估
  不做，bracketed paste 落地后可重估）、输入模式可见性（做题页 vs
  对话页的提示恒显）、长输出页（/model /sessions）的分页体验。

### 6.2 出题匹配粒度：同概念域 ≠ 同考察点

- 现象：用户刚与教练对练「unwrap_or vs unwrap_or_else 急切/惰性求值
  （白分配问题）」，说「出个题吧」；教练 topic 正确指向该考察点，
  但 L1 的 LLM 选了 option-and-then-chain（**and_then+map 链式改写**，
  同属 types.option-result 但考察点不同）。用户「感觉你要考的不是
  这个」，教练在后续轮次承认错配（会话 [38]–[45]）。
- 根因：题库无「unwrap_or vs unwrap_or_else 求值时机」模板；LLM 选
  模板的 no_match 判据太松（同概念域即视为相关）。
- 修法候选：
  1. `llm_pick_template` 的 prompt 收紧：**必须训练用户要求的具体
     手法/行为，同域不算匹配** → no_match 走 L2/L3（自由生成恰好
     适合出这类精确对题的题）；
  2. 模板批次二新增主题：「unwrap_or/map_or 与 *_else 变体的急切 vs
     惰性求值」（正好衔接课程与本次实测）；
  3. 出题工具的返回值带**匹配依据**（哪层/为何选此模板），教练发现
     错配时应**主动重新出题**而非道歉了事。

### 6.3 对话内悬而未决任务无跟进（M5 复盘交互必须覆盖）

- 现象：教练帮用户改写代码后，用户逐个贴改写验证（这部分正常，每条
  都 check_code）；但话题一转开（出题），教练**不会主动回访**之前
  未完结的代码任务（「离开那个对代码提问后他就不会自己去看了」）。
- 现状：练习状态有回流（index → system prompt 的 practice_note），
  但**对话内的 open loop**（贴过的代码、待验证的改写、用户未答的
  问题）没有任何注入——全靠模型「自觉」，而它不会。
- 修法候选：仿 practice_note 加「对话 open-loop 摘要」注入（最近
  讨论的代码任务/待验证项）；system prompt 加跟进原则（话题转开前
  有未验证改动时主动询问回访）。**M5 的 follow-up 决策设计时一并
  落地，不要单做。**
